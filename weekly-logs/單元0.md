單元 0：拖拉式 AI Agent 導覽與平台初探

日期： 2026/09/20 本週對應課綱單元： 單元 0

學到的知識點

這一週最主要的收穫，其實不是某個技術，而是課綱裡寫的那句學習思路： 應用場景 → 核心名詞 → 知識結構。順序是反過來的——不是先把技術學完再想要用在哪， 而是先確定「我要解決什麼問題」，再回頭去抓需要哪些知識點。這點對我後面選平台、 選部署管道的判斷影響很大。

其次是搞清楚 Agent 跟一般聊天機器人的差別。傳統的關鍵字客服機器人是「問 A 答 A」的對照表， 問法一換就答不出來；Agent 則是由幾個可以組裝的零件構成的：一顆負責理解與生成的 LLM、 一份決定角色與行為規範的 System Prompt、一段能記住使用者說過什麼的 Memory、 一個放自有資料的知識庫（RAG）、可以對外做事的 Plugin / Tool， 把這些串起來的 Workflow，以及防止它亂講話的 Guardrail。 課綱單元 1 到 8 基本上就是逐一拆解這幾個零件，單元 9 是把組好的東西接到真實使用者面前。

我也順便建立了對這些名詞的初步理解，之後每一單元會再補細節：LLM 的參數（Temperature、 Max Tokens、Context Window）決定回覆的穩定度與長度；RAG 是讓模型能引用自有資料、 減少幻覺的作法，中間牽涉到切片（chunking）、向量化（embedding）與相關性排序； Guardrail 除了防止模型講錯話，也要擋 Prompt Injection 這種刻意誘導的攻擊。 低代碼平台（Coze、Dify 這類）的角色，就是把上述零件包成現成模組，讓不具備程式背景的人也能組裝。

我做了什麼（實作紀錄）

建立了 GitHub 帳號下的第一個 repo，並完成 README 初版，內容包含專案背景、產品構想、 使用場景、技術路線與各單元對應規劃。同時建立 weekly-logs/ 資料夾，用來放每週的學習文件。

技術平台部分，比較了 Coze 與 Dify 之後選定 Dify。老師說明不一定要用 Coze， 而 Dify 是開源的、介面同樣是拖拉式 workflow、知識庫與記憶等模組都是現成的， 學習曲線相近但彈性更高，也能自架，後續要串自有網站或其他管道比較不受限制。

對應到我的專案

這週最大的轉折是專題方向。我原本的構想是做客服型 agent，把重複回答的工作自動化， 目的是幫自己省時間，也就是節流。跟老師討論後方向被翻轉成開源：與其優化「已經找上門的人」， 不如把 AI 放到「陌生人變成有效名單」這一段。最後決定本學期先做轉換端的選種顧問 agent， 行有餘力再做廣告素材產出的 agent。

另一個調整是部署管道。課綱單元 9 預設是一鍵發布到 LINE，但我的實際流量是 Meta 廣告 → IG/FB 留言或私訊，如果要求訪客額外跳去開 LINE，中間會多一次不必要的平台切換， 本來就是低涉入的冷流量會在這裡流失掉一大半。所以我把部署順序改成： 第一優先接 Meta Messenger / IG 私訊或網站嵌入，LINE 降級成轉換後期的關係維護管道。 這是這週我自己覺得最有價值的一個判斷——技術上怎麼做是一回事， 但部署在哪裡必須對得上使用者實際的行為路徑，不然做得再好也接不到人。

遇到的問題與解法

第一個是完全沒建過 GitHub repo，不知道該從哪裡開始。照老師在課綱裡建議的方式， 直接問 AI 要我一步步帶，從建立 repository、設定 public、編輯 README 到 commit， 跟著做一次就通了。這件事本身也印證了單元 0 的學習思路：不需要先把 Git 的完整概念讀完， 先讓它跑起來，缺的觀念在使用過程中再補。

第二個問題比較麻煩：我想接的 Meta Messenger / Instagram，並不在 Dify 一鍵發布的清單裡 （清單上是 LINE、Discord、Telegram、網頁）。查過之後確認做法是可行的—— Dify 的每個應用都可以發布成 API，外部程式能呼叫它並取得回覆， 所以架構會變成三段：Meta 的 Webhook 把留言或私訊事件推出來，中間用 n8n 這類工具當橋接層， 負責接住事件、呼叫 Dify API、再把回覆送回 Meta，而 Dify 依然只專心當 agent 的大腦。 這段還沒實作，但已經確認路是通的，留到單元 9 再動手。

老師的迴饋（若有）

建議把專題方向從節流（客服自動化）轉向開源（用 AI 拓展客源），這是本週方向調整的主因。
