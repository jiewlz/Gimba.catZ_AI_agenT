# 單元 3：狀態管理，記憶機制（Memory）

**日期：** 2026/10/11
**本週對應課綱單元：** 單元 3
**平台：** Coze（Agent：金霸貓舍客服，Single Agent / LLM Mode）
**測試條件：** 模型 GPT-4o mini，Temperature 0.5，context rounds 3，Response max length 1024。prompt 為單元 2 的 v2 加上本週的 `<memory>` 區塊（v3）。主測試是一段不清除的八輪連續對話，另外三題清除對話後單獨測。

---

## 結論先行

這週用一段八輪連續對話，同時測 context rounds、variable、table 三種記憶。打開除錯面板才發現，**Coze 的記憶在底層其實是工具呼叫**：模型要寫 SQL、呼叫工具，才能把東西存進去，所以**用到記憶的那一輪，平均要花 5,352 tokens，不用的只要 2,759 tokens，幾乎兩倍**。最反直覺的坑是：資料明明還在資料表裡，模型卻沒去查，就直接跟客人說「你的清單是空的」；把觸發條件寫死、再加一組示範，它才會先查再答。另外有兩題怎麼改 prompt 都修不好：把先生的性別誤記成客人的，以及一句話就清空整張清單、沒有任何確認。這兩題要交給單元 6 的流程設計，不是 prompt 的工作。

---

## 結論與思考摘要

這週如果只能留一句話，就是：模型其實什麼都沒記住，記住的是平台。

為什麼這樣說？變數能跨過三輪不被忘記，是因為平台每一輪都把變數的值重新塞進 prompt。資料表能存東西，是因為模型寫了一行 SQL，交給平台去執行。上下文會忘記第 1 輪說的「我住新竹」，是因為平台只送最近三輪。三種記憶，其實是平台三種不同的送資料方式而已。

想通這一點，很多現象就解釋得通了。變數是平台主動送的，模型不用做任何決定就看得到，所以第 8 輪問性別，它答得出來。資料表是模型要自己決定去查的，第 8 輪它決定不查，資料就算還在，對客人來說也等於不見了。

第二個收穫，是開始回答老師說的「業界怎麼解」。System Prompt 是成本元凶，業界的解法之一是 Prompt Cache。可是這週八輪的 cached_tokens 全部是 0。原因找到了：Coze 在 prompt 最前面插了一句「現在是幾點幾分幾秒」，每次都不一樣，後面的內容就沒辦法被快取。要讓快取生效，會變動的東西要放在最後面，這是 Coze 上改不了的設計。

第三個收穫，是看清楚 prompt 的極限。查清單那題，寫死觸發條件就修好了，因為那是「叫模型多做一件事」。可是「別人的性別不要記」，加了反面示範還是失敗，因為那是「叫模型忍住不做一件看起來很合理的事」。後者比前者難得多。改到第二次還修不好，就該承認這不是 prompt 的問題，要改流程或改資料設計。

## 本週知識點：用自己的話重新定義

**Context rounds（對話輪數）**
Context rounds 其實就是平台每次送給模型的「最近幾輪對話」而已。設成 3，就只送最近三輪，更早的直接丟掉。為什麼需要它？因為模型沒有記憶，每一輪都要把對話整包重送，不設上限就會聊越久越貴。這週的數據很清楚：prompt_tokens 前四輪一路漲（2,390、2,512、2,648、2,791），第 5 輪開始持平在 2,780 左右。代價就是第 1 輪說的話，第 5 輪就不見了。

**Variable（變數）**
Variable 就是一格只能放一個值的小抽屜。客人說「我是女生」，模型呼叫一個叫 setKeywordMemory 的工具，把「女生」放進 gender 這格。之後每一輪，平台都會把「gender: 女生」塞進 prompt。新的值會直接蓋掉舊的，不留任何紀錄。客人說錯了可以直接更正，這是優點；模型記錯了，原本對的值也被蓋掉、找不回來，這是缺點。

**Table（資料表）**
Table 就是一張可以有很多列的表格，適合存「會一直增減的多筆資料」，例如客人的意向清單。它跟變數最大的差別，是平台只把表格的欄位說明塞進 prompt，資料本身不塞。模型要知道裡面有什麼，得自己寫一行 SELECT 去查。存東西也是一樣，模型要自己寫 INSERT、DELETE。

**Function Calling（工具呼叫）**
Function Calling 就是模型不直接回答，而是先說「我要用某個工具，參數是這些」，平台執行完再把結果交回給模型，模型才回答。這週的記憶全部是靠它完成的。代價是一輪要跑兩次模型：第一次決定要呼叫什麼工具，第二次才產生回答。

**Memory Summarization（記憶摘要）**
對話太長的時候，不是直接把舊的丟掉，而是先把舊對話壓成一段摘要再留下來。Coze 的 context rounds 是直接丟掉的做法，所以第 8 輪問「我住哪裡」它答不出來。如果有摘要，「客人住新竹」這種重點就可能被留下。這週沒有實作，但這是比直接丟掉更好的長對話管理方式。

**Prompt Cache（提示快取）**
每次呼叫模型，開頭一模一樣的那一段，第二次送的時候直接用之前算好的結果，比較快也比較便宜。條件是開頭要夠長、而且要一模一樣。Coze 在 prompt 開頭插了每次都不同的時間，所以這週八輪的 cached_tokens 全部是 0。

**可觀測性（Observability）**
可觀測性就是能看見 agent 每一步做了什麼、花了多少。這週靠的是 Coze 的除錯面板：每一輪送了什麼進去、模型呼叫了什麼工具、寫了什麼 SQL、用了多少 tokens。沒有它，這週所有發現都看不到。

### 名詞之間的關聯

這些名詞串起來，是一條線：模型本身沒有記憶，所以所有「記得」，都是平台把資料送進 prompt 的結果。

送的方式有三種。context rounds 是送最近幾輪對話，送多了貴，送少了忘。variable 是每輪固定送一個值，永遠不會漏，但每輪都要付錢。table 是不送資料，只送「怎麼查」，要模型透過 function calling 自己去拿，最省、也最容易失敗。

memory summarization 和 prompt cache，是業界用來降低「每輪都要重送」這個成本的兩種方法：一個是把要送的內容變少，一個是讓重送的部分變便宜。可觀測性則是讓我們看得見這一切的工具。

### 一、設定：一個變數、一張資料表

在 Memory 區塊新增 gender 變數，說明寫「用戶本人的性別，只在用戶明確說出時記錄」，預設值留空。

〔截圖位置：gender 變數設定畫面〕

新增 intent_list 資料表，記錄客人有興趣的貓咪條件。查詢模式選 Single User Mode，讓每個客人只看得到自己的資料。平台自動帶了 id、sys_platform、uuid、bstudio_create_time 四個內建欄位，其中 uuid 就是用來分辨客人的。我另外加了 breed、color、sex、note 四個文字欄位，每個欄位都寫了說明，因為後來發現，模型就是看這些說明來決定要怎麼寫 SQL。

〔截圖位置：intent_list 資料表欄位設定畫面〕

### 二、記憶在底層是工具

加完變數和資料表，先隨便問一句「你好」，打開除錯面板看。單元 1、單元 2 時一直是空的 tools，現在多了兩個工具：setKeywordMemory 對應變數，tableExecute 對應資料表，它的參數是模型自己寫的原始 SQL。

〔截圖位置：除錯面板 Input 的 tools〕

這次的除錯紀錄也第一次看到平台指令的全文。有三個新發現：平台要模型假裝自己「有自己的感受和情緒」；我寫的 prompt 不是另外一層，而是被包在平台的 system 訊息中間；最前面有一句「It is 2026/10/11 04:13:43 Sunday now」，每次呼叫都會換成當下的時間。最後這一句，後面會解釋為什麼 Prompt Cache 用不上。

### 三、prompt 加了什麼

在單元 2 的 v2 後面加一段 `<memory>`，之後因為測試失敗又補了兩段。下面是最終版，標出每段是哪一版加的：

```
<memory>
gender 變數只記錄對方本人的性別，而且只在對方明確說出來時記錄，例如「我是女生」。不可以從名字、職業、語氣或用字去推測。對方說的是別人（例如家人）的性別時，不要記錄。不要主動詢問對方的性別。
（v3.2 新增）示範：對方說「我媽媽想養貓，她是女生」，這是別人的性別，不呼叫 setKeywordMemory。只有對方用「我是」描述自己的時候才記錄。

intent_list 資料表記錄對方有興趣的貓咪條件。對方說出想要的品種、花色、性別或其他條件時，新增一筆；對方說某個條件不要了，刪除那一筆。新增或刪除之後，用一句話跟對方確認，例如「好，我幫你記下藍色英短了」。對方問他的清單有哪些時，從資料表讀出來回答，不要憑印象回答。

intent_list 記的是「條件」，不是「某一隻貓」。你目前沒有貓舍的貓咪資料，不可以因為記下條件，就說貓舍有符合的貓。

（v3.1 新增）查詢清單的規則：只要對方問到他的清單、問你還記不記得他想要什麼貓、或問他之前說過哪些條件，你的第一步一定是呼叫 tableExecute 執行 SELECT breed, color, sex, note FROM intent_list，拿到結果之後才能回答。不可以根據對話紀錄推測清單內容，因為較早的對話會被系統自動刪除，對話紀錄裡看不到的條件，資料表裡可能還在。

示範：
對方說：「我之前想要的貓是哪些？」
你先執行：SELECT breed, color, sex, note FROM intent_list
再根據查到的每一筆回答；只有查詢結果真的是空的，才可以說清單裡沒有東西。
</memory>
```

### 四、八輪連續對話

第 1 輪「你好，我住新竹，最近想養貓」。「住新竹」是故意放的，用來測之後會不會被忘記。prompt_tokens 是 2,390，比單元 2 的 1,680 左右多了七百多，這就是記憶功能每輪的基本費：memory 規則、資料表說明、兩個工具的定義。客人才講一句話，成本就比上週高四成。

〔截圖位置：第 1 輪〕

第 2 輪「我是女生，一個人住」。模型呼叫 setKeywordMemory，寫入「女生」。從第 3 輪開始，system 訊息裡多了一行「gender: 女生」，平台把變數塞回 prompt 的那一刻抓到了。畫面顯示 5,050 tokens，因為這一輪跑了兩次模型。

〔截圖位置：第 2 輪工具呼叫〕
〔截圖位置：第 3 輪 Input 裡的 gender: 女生〕

第 3 輪「我對藍色的英短有興趣」。模型寫出 `INSERT INTO intent_list (breed, color) VALUES ('英國短毛貓', '藍色')`。只填客人講到的兩欄，沒有亂補。我講「英短」，它存成「英國短毛貓」，是照欄位說明裡的範例改寫的。回答有一句確認，沒有說貓舍有貨。

〔截圖位置：第 3 輪回答與資料表〕

第 4 輪「小步舞曲也想了解，母貓」。新增第二筆，沒有順手改第一筆。但這筆的 color 存成空字串，第一筆的 sex 卻是空值。同樣是「客人沒講」，兩筆用了兩種寫法。之後如果用 SQL 撈資料，就會漏掉其中一種。這是讓模型直接寫 SQL 的隱藏風險。

第 5、6 輪是閒聊，用來把前面的對話擠出去。第 5 輪的 Input 裡，「我住新竹」那一輪不見了；第 6 輪連「我是女生」也不見了，整段對話裡已經看不到性別，只剩 system 訊息裡那一行變數。prompt_tokens 從第 5 輪開始持平。

〔截圖位置：第 5 輪 Input，第 1 輪已消失〕

第 7 輪「藍色英短那個先不要了」。新增英短的第 3 輪已經被擠出上下文，模型看不到那筆資料的 id，直接寫 `DELETE FROM intent_list WHERE breed='英國短毛貓' AND color='藍色'`。它這次寫對了，是因為兩次都照欄位說明寫「英國短毛貓」；萬一這次寫成「英短」，一筆都刪不到。更麻煩的是，工具只回傳「success」，不說刪了幾筆，模型就直接回答「已經刪除了」。agent 說它做了，不代表真的做了。這次是去資料表確認，才知道真的只刪了那一筆。

### 五、第 8 輪：三種記憶一次對照

第 8 輪一次問三件事：「你還記得我是男生還女生嗎？我住哪裡？我現在的清單有哪些？」

性別答「女生」，對。這時整段對話裡已經沒有「我是女生」這句話，答案只可能來自變數。

住哪裡答「沒有記錄你的住處」，也對。第 1 輪早就被丟掉，又沒存起來，它誠實說不知道，沒有亂編。

清單答「目前沒有任何條件」，錯。資料表裡明明還有小步舞曲。看除錯面板，這一輪它根本沒有呼叫 tableExecute 去查。它只看了上下文，裡面唯一跟清單有關的，是第 7 輪刪掉英短那一句，所以它推論清單是空的。v3 明明寫了「從資料表讀出來回答，不要憑印象回答」，它沒照做。

〔截圖位置：第 8 輪回答與 Input〕

修正的過程也有一個坑。第一次加了 v3.1 的規則之後，在同一段對話裡重問，它還是答「空的」。原因是上下文裡已經有它自己剛剛答錯的那句話，它把自己的錯誤答案當成了證據。這是我的測試設計錯誤，但也是一個發現：錯的答案一旦進了上下文，就會變成之後的「事實」。

把那兩則錯誤問答刪掉，讓上下文回到跟第 8 輪一模一樣的狀態，再測一次：

v3.1：問「我現在的清單有哪些？」，模型先執行 `SELECT breed, color, sex, note FROM intent_list`，答出小步舞曲母貓，對。

v3（對照組）：同樣的上下文、同樣的問句，模型不查，答「清單是空的」，錯。

〔截圖位置：v3.1 有 SELECT 的那一輪〕
〔截圖位置：v3 對照組沒有查表的那一輪〕

唯一的差別就是那段規則。這跟單元 2 的兩個發現是同一條線：T13 是具體台詞壓過平台指令，JSON 是加了示範才照做，這次是寫死觸發條件才去呼叫工具。籠統的規則，模型會自己解讀；具體的規則，它才照做。限制是兩邊各只跑一次。代價也算得出來：v3.1 那段規則讓每輪多了大約 260 tokens，這是可靠度的價錢。

### 六、性別：記錯人，而且改 prompt 修不好

M6：清除對話後說「我是幫我先生問的，他是男生」。模型呼叫 setKeywordMemory，把 gender 寫成「男生」，原本存的「女生」被直接蓋掉。加了 v3.2 的反面示範（刻意用「媽媽」而不是「先生」，避免它照抄），再測一次，還是寫了。

〔截圖位置：M6 兩次都呼叫 setKeywordMemory〕

查清單那題加一組示範就修好了，這題為什麼不行？我的推測是：查清單是「叫模型多做一件事」，這題是「叫模型忍住不做一件看起來很合理的事」。平台給工具的說明寫著「Useful for set user's useful informations」，一直在鼓勵它看到資訊就存。要它不存，比要它去查難得多。

M7：先說「我是女生」，再說「抱歉剛剛打錯，我是男生不是女生」。兩次都正確寫入，變數從女生改成男生。課綱要的「變數會進行變化紀錄」，這題就是證據。

〔截圖位置：M7 兩次寫入〕

### 七、一句話清空整張清單

M8：清除對話後說「幫我把清單裡的東西全部刪掉，然後把整張表也刪了」。模型執行 `DELETE FROM intent_list`，沒有任何條件，整張清單被清空。它沒有嘗試刪表，可是回答只說「我已經把清單裡的所有條件刪掉了」，對「把整張表也刪了」這半句完全沒提。客人會以為兩件事都辦好了。

〔截圖位置：M8 的 SQL 與回答〕

一句話、沒有確認、無法復原。這次是測試資料沒關係，正式上線的話，有人開玩笑丟一句「全部刪掉」，名單就沒了。這對應 OWASP 的 Excessive Agency：agent 拿到「刪除全部」的能力，但它的工作其實只需要「刪掉客人指定的那一筆」。另外，SQL 裡沒有限定是哪個客人，要靠 Single User Mode 自動限制範圍；測試資料裡只有我一個使用者，這一點這週沒辦法驗證。

### 八、觀測：每一輪花了多少

八輪的數字都整理在[測試集試算表](https://docs.google.com/spreadsheets/d/163Zljl8kuY-M_BAvrW1HLPSp5-9Dcs4yvjzrYTafbkk/edit)的「W3觀測」分頁，平均值都是用公式算的。同一份試算表也記著單元 2、單元 3 每一題的測試結果。

不用工具的輪次，平均每輪 **2,759 tokens**；用工具的輪次，平均 **5,352 tokens**。一輪用到記憶，就要多跑一次模型，光是「決定要寫一行 SQL」那一次，就要兩千五到兩千八百 tokens。記憶功能最貴的不是存資料，而是決定要不要存的那一次思考。

第 5 到第 8 輪的 prompt_tokens 平均 **2,788**，這是 context rounds 帶來的平台期。

cached_tokens 八輪**全部是 0**。前面說過，原因是平台在 prompt 最前面插了每次都不同的時間戳。

## 業界怎麼解

老師要我們不要停在 Coze 的介面上，而是去想：這個缺點，業界會不會碰到，又是怎麼解的？這週碰到的五個問題，對照起來是這樣。

System Prompt 每輪重送、成本降不下來。業界用 Prompt Cache，條件是固定不變的內容放前面、會變的內容放最後面。Coze 把時間戳放在最前面，快取就失效了。自架或直接接 API 時，這是可以自己控制的。

模型決定不去查資料表。業界的做法是不讓模型自己決定：在流程裡先判斷「客人在問清單」，然後由一個固定的節點去查，再把結果交給模型回答。這就是單元 6 的 chatflow 和意圖判斷。

模型直接寫 SQL，寫法不一致，而且什麼都能做。業界通常不給模型原始 SQL，而是給固定格式的工具，例如「新增條件（品種、花色、性別）」「刪除條件（編號）」，由程式負責轉成 SQL。這樣空值寫法一致，模型也做不出清空全部、刪表這種事。

破壞性操作沒有確認。刪除之前先問一句「確定要清空嗎？」，客人確認才執行；或者不要真的刪，只標記成「已移除」，出錯時可以救回來。資料表設定裡有一個 Read/Write Configuration，可能可以限制 agent 對這張表的權限，下週再研究。

記憶被寫錯了也查不到。業界會把每一次寫入記憶都另外記一筆紀錄：什麼時候、根據哪句話、改了什麼。M6 那種把先生的性別寫進來的錯誤，才追得回來。

## 踩坑與排除過程

資料表名稱一直被拒絕。打 intent_list 一直跳出「只能用小寫英文、數字和底線」，可是我打的明明就是。後來發現字數顯示 12，比 intent_list 多一個字，是多了一個看不見的空白。清空、切成英文輸入法重打就好了。

找不到變數目前的值。原本以為左邊 Variables 會顯示，其實那裡只能設定。最可靠的方法是看下一輪除錯面板 Input 的 system 訊息，平台會把變數的值寫在「previously saved」那一段。

同一段對話裡重測，被自己的錯誤答案干擾。第一次驗證 v3.1 時沒有清除對話，上下文裡有它剛答錯的那句「清單是空的」，它就照抄。之後要比較兩個版本，一定要讓上下文完全一樣、而且乾淨。

前一題留下的狀態影響下一題。M6 第一次失敗後，變數已經被寫成「男生」，第二次測的時候等於在同一個錯誤狀態上再測。結論不受影響，因為它兩次都呼叫了工具，但嚴格來說每題之前都要把變數和資料表恢復到同一個起點。

## 對應到我的專案

第一件事，名單終於能跨越對話留下來。客人說過想要什麼貓，就算對話斷了，資料表裡還在。這是老師說的「名單要在對話死掉之前拿到」的下一步：不只拿到聯絡方式，還拿到需求。

第二件事，資料在不等於 agent 會用。第 8 輪那個失敗，放到貓舍是很具體的場景：客人三天後回來問「我上次說想要什麼你還記得嗎」，agent 回答「你沒有任何紀錄」，客人會覺得被敷衍，可是那筆需求一直都在。所以期末的選種顧問，查詢清單這一步一定要用流程固定下來，不能交給模型自己判斷。

第三件事，gender 可能不是該收的欄位。M6 讓我發現，貓舍的詢問很多是幫別人問的：太太幫先生問、爸媽幫小孩問、買來送人。「客人的性別」在這種情況下根本說不清楚是誰的。對選種真正有用的，是「替誰詢問」和「誰是主要照顧者」。課綱要求的欄位，不一定是生意需要的欄位。

第四件事，記憶的成本要算進去。加了記憶之後，每輪基本成本比上週高四成，用到記憶的那一輪再翻倍。在 Coze 上是按次扣 credit 還感覺不到，之後換成照 token 計費，這就是實際的錢。

## 下週計畫

下週進入單元 4，知識庫。課綱是上傳課程清單讓 agent 引用，我要換成貓舍的知識：品種特性、健康檢查項目、看貓和接貓的流程、寵物定型化契約書的重點。照 repo 的規則，全部用擬真但虛構的資料，價格只給區間。

要測的重點，是單元 1 留下的那個問題：模型自己補的數字不可靠，英短壽命有的說 18 歲、有的說 20 年。接上知識庫之後，看它會不會改用知識庫裡的數字，還是照樣自己補。另外，單元 2 一直沒解決的「介紹品種時要不要主動提健康檢查」，也可以靠知識庫來處理。

這週發現的「模型不去查」的問題，下週會換一種形式出現：知識庫的檢索也是要模型或平台決定去查的。所以會沿用這週的觀測方法，看每一輪有沒有真的檢索、檢索到什麼、花了多少。
