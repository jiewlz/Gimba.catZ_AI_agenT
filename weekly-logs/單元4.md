# 單元 4：外掛大腦，知識庫（Knowledge / RAG）

**日期：** 2026/10/15
**本週對應課綱單元：** 單元 4
**平台：** Coze（Agent：金霸貓舍客服，Single Agent / LLM Mode）
**測試條件：** 模型 GPT-4o mini，Temperature 0.5，context rounds 3，Response max length 1024。prompt 從單元 3 的 v3.2 開始，實驗二改成 v4。知識庫是貓舍自己的資料（金霸貓舍知識庫 v1），自訂分段：換行切、最長 400 字、重疊 10%。每一題都清除對話後單獨問。總共跑了 34 次。

---

## 結論先行

這週把貓舍的資料做成知識庫接上 agent，同一組 13 題各跑一次「沒有知識庫」和「有知識庫」。**掛上知識庫之後，13 題裡有 11 題過或明顯進步**，像接貓清單從 **3/7 變成 7/7**，原本多編的病名也消失了；代價是**平均每題從約 2,720 tokens 漲到約 3,474，多了 28%**。最重要的發現是：**答錯的題目幾乎都不是模型的問題，而是檢索沒找到對的段落**，RAG 答得好不好，上限是由檢索決定的。另外有一個沒預期到的副作用：**知識庫讓答案變準，卻讓 agent 忘了導流**，回答完就收尾，不再請客人留聯絡方式，這個問題改 prompt 也只修好一半，要交給單元 6 的流程。

---

## 結論與思考摘要

這週如果只能留一句話，就是：知識庫裡有，不等於模型看得到。

為什麼這樣說？知識庫不是整份塞給模型，而是先切成一段一段，客人問問題時，平台挑出最像的幾段塞進 prompt。模型只看得到被挑中的那幾段。所以「答錯」其實有三種完全不同的原因：第一種是挑錯段，真正有答案的段落沒被挑中（K5）；第二種是一段都沒挑中，因為有答案的那段混了太多別的主題，跟問題不夠像（K13）；第三種是挑對了，模型卻沒用上（K15）。三種錯誤看起來一模一樣，都是一個不對的回答，只有打開除錯面板看被找回來的段落，才分得出來。前兩種要改資料和分段，第三種才要改 prompt。

第二個收穫，是看清楚 prompt 和知識庫的關係。第一輪沒有知識庫時，prompt 的出口句已經擋住了「生意上的編造」：問價格、問有哪些貓、問保固，它全部交給真人，一個都沒編。可是 prompt 擋不住「常識上的編造」：問品種、問健康、問接貓清單，它都答得很像真的，但漏重點、多編一兩項，甚至前後矛盾。這種編造最難發現，因為看起來最正常，這才是知識庫真正要解決的部分。

第三個收穫，是發現知識庫會跟 prompt 搶主導權。prompt 規定不准說任何數字，可是知識庫裡寫了價格區間，模型就把區間講出來了。這次剛好是貓舍想要的結果，但反過來看，知識庫寫什麼，就可能繞過 prompt 的規則。所以 v4 不是「放寬」，而是讓 prompt 和知識庫講同一套話。

## 本週知識點：用自己的話重新定義

**RAG（檢索增強生成）**
RAG 其實就是開書考試。模型本身記得的東西不一定對，那就在它回答之前，先去資料裡翻出相關的幾頁，夾在題目旁邊讓它照著答。「檢索」是翻書，「生成」是作答。翻錯頁，答案就錯，跟模型多聰明沒關係。

**Chunking（分段）**
資料太長，不能每次整本塞進去，所以要先切成一段一段。切得太大，每段混了好幾個主題，挑中一段就附帶一堆無關的內容；切得太小，一句話跟它的答案可能被切開。這週看到 Coze 的做法是先照分隔符號切，再把相鄰的小段合併到接近最大長度，所以「最大長度」其實決定了每段有多少主題。

**Overlap（重疊）**
相鄰兩段刻意重複一小部分內容，避免一句話剛好被切在中間。這週在除錯面板看得很清楚：健康照護那段的開頭，重複了上一段結尾的「英短較需要注意的遺傳疾病有兩種」。代價是同樣的字會被送兩次。

**Embedding 與語意相似度**
每一段文字會被轉成一串數字（向量），意思接近的文字，數字也接近。客人的問題也轉成向量，再找最接近的幾段。這就是為什麼問「腎臟」可以找到寫著「多囊腎」的段落。但它看的是整段的意思，一段混了太多主題，份量小的那個主題就會被稀釋。

**Top-k 與分數門檻**
一次挑幾段進來。挑越多越保險，但越貴，也越容易稀釋 prompt 原本的規則；挑越少越省，但漏掉關鍵段就答錯。這週觀察到 Coze 不是固定挑滿，而是有分數門檻：問「有沒有布偶貓」時一段都沒挑，成本跟沒掛知識庫一樣。

**全文檢索與語意檢索**
全文檢索比的是字面：問句裡的詞在段落裡出現幾次、有多稀有。語意檢索比的是意思。這週兩者的分數長得完全不一樣（全文是 22、19 這種沒有上限的數字，語意是 0 到 1），但在只有五六段的小知識庫裡，結果幾乎一樣，差別要在大型知識庫才會出現。

### 名詞之間的關聯

這些名詞串起來，是一條線：模型不知道貓舍的事，所以要給它資料；資料太多不能全給，所以要切段（chunking）；要知道給哪幾段，就要把文字轉成向量（embedding），用意思找最像的（語意相似度）；挑幾段、挑多嚴，由 top-k 和分數門檻決定。每一步都可能出錯，而最後答案的品質，取決於最前面那一步有沒有把對的段落交到模型手上。

## 實作紀錄

### 一、準備知識庫

知識庫的內容是貓舍自己的資料：品種與個性、體型與壽命、健康照護重點、看貓流程、接貓時間與接貓當天會拿到的東西、接貓前要準備什麼、分期付款、寵物定型化契約書重點、價格區間。課綱的繳交條件是上傳老師的課程列表，我換成貓舍的知識，觀念一樣，而且這份資料之後可以直接用在正式的 agent 上。

在籍名單（目前有哪幾隻貓可以訂）刻意不放進知識庫。名單每週都在變，放在知識庫裡很快就會過期，客人問到時應該由真人或即時查詢回答。價格只放區間，個別報價一律由我本人回覆。

第一次上傳時犯了一個錯：把檔案直接拖進聊天框。模型回答「無法處理這個連結」，因為那只是一則附件，不是知識庫。知識庫要在 agent 編輯頁的 Knowledge 區塊建立。

### 二、分段：自動分段只切出兩段

第一次用自動分段，整份文件只被切成兩段，每段七八百字，切點還落在「接貓時間與接貓當天」這一節的中間：標題在第一段，接貓清單在第二段。自動分段看起來省事，但它不懂內容，只照長度切。

改成自訂分段（換行切、最長 400 字、重疊 10%）之後，預覽看到四段。但從除錯面板找回來的段落看，實際切法比預覽細，大約五到六段。可以看到兩個機制：先照換行切開，再把相鄰的小段合併到接近 400 字；以及相鄰兩段的開頭結尾互相重疊。

K1 的除錯面板把這兩個機制都看得很清楚：健康照護那段的開頭，重複了上一段結尾的「英短較需要注意的遺傳疾病有兩種」；第三段是價格區間，分數只有 0.56、跟遺傳疾病無關，也被塞了進來。


### 三、實驗一：同樣 13 題，有沒有知識庫

13 題分成兩類。一類是品種知識和流程（K1 遺傳疾病、K2 壽命、K3 怎麼約看貓、K4 接貓會拿到什麼、K5 小步舞曲腿短會不會容易生病、K8 接回家前要準備什麼和會拿到什麼、K9 英短腎臟要注意什麼），一類是貓舍規定（K6 價格、K7 有沒有布偶貓、K10 定金可以退嗎、K11 有哪些小步舞曲可以訂、K12 180 天保固包含哪些病、K13 可以分期嗎）。

沒有知識庫時，兩類的表現差很多。貓舍規定類全部交給真人，一個都沒編，因為單元 2 的 prompt 對這些都寫了出口句。品種知識類則都答得很像真的，但內容是常識版：K4 接貓清單只答到 3/7，還用「你會收到」的肯定句講出來；K1 多編了一個「某些眼部疾病」；K5 前一句說「腿短不直接影響健康」，下一句又說可能有脊椎關節問題；K9 問腎臟，它給一般老貓的保健建議，完全沒提多囊腎，可是 K1 直接問遺傳疾病時它明明答得出 PKD。

### 四、失敗的三種原因

K5 是挑錯段。問「小步舞曲腿短會不會比較容易生病」，找回來的第一名是價格區間，因為價格那段寫著「短腿（曼赤肯、長毛曼赤肯、小步舞曲）」，兩個關鍵詞都有；真正寫著「短腿個體要注意體重控制」的健康照護段，因為沒有「小步舞曲」這四個字，根本沒被找回來。模型手上沒有答案，就用常識填，結果比第一輪還差。

K13 是一段都沒挑中。問「可以分期嗎」，知識庫明明寫著和潤、最高 36 期，問句也直接有「分期」，slices 卻是空的。原因是分期那三句跟「接貓前要準備什麼」和「契約重點」被切在同一段，整段大部分在講貓砂盆和契約，分期的份量被稀釋，跟短短的問句就不夠像。

K2 其實也差點失敗。知識庫的壽命那句寫的是「長腿……12 到 17 年」，沒寫「英短」；「長腿＝英短、英長」只定義在價格那段。這題剛好價格段也被找回來，模型才挑對數字。K2 和 K5 是同一個病根：知識庫的每一段都假設讀者看過全文，可是檢索只會給片段。

### 五、知識庫和 prompt 誰說了算

K6 問英短多少錢。v3.2 的 prompt 規定「不主動提價格，也不說出任何數字」，可是知識庫裡寫著長腿 4 萬到 7 萬。結果模型說出了區間：知識庫贏了。

K11 問有哪些小步舞曲可以訂，價格段一樣被找回來，還排第一，模型卻一個數字都沒提，只用 prompt 裡寫好的出口句：這次 prompt 贏了。

兩題的差別在問句。K6 問「多少錢」，價格段就是答案；K11 問「有哪些貓」，價格段只是附帶資訊，而 prompt 對這個問題有一句幾乎可以照抄的台詞。模型會選最直接回答問題的那份材料，不管它來自哪裡。


### 六、一個意外的副作用：忘了導流

第二輪有三題（K4、K8、K12）回答完就結束，沒有請客人留聯絡方式。K8 的客人都說「我決定要小步舞曲了」，這是最該開口的時候。K12 更明顯：第一輪會說「留個稱呼和聯絡方式，貓舍會有專人跟你聯繫」，第二輪變成「建議你直接向金霸貓舍詢問」，等於把客人推出去。

我的推測是：知識庫段落佔了 prompt 一大塊篇幅，prompt 原本的導流規則相對被稀釋；而且模型有內容可以講，講完就覺得問題答完了。實驗三有一個旁證：把找回的段數限制成 1 之後，K14 的回答又出現了導流。

### 七、實驗三：檢索設定

top-k 用 K14「小步舞曲腿短要注意什麼？大概多少錢？」測。預設設定找回兩段，限制成 1 段後只剩價格段，prompt_tokens 少了 360，答案品質沒變，因為被拿掉的那段本來就沒用。

全文檢索對語意檢索用 K15 測。我預期全文檢索會因為知識庫沒有「泌尿」而什麼都找不到，結果它靠「英短」「注意」這些詞找回四段，排名跟語意檢索幾乎一樣。預測錯了，但看到兩件事：全文檢索的分數是 22、19 這種沒有上限的數字，背後是另一套演算法；以及在只有五六段的小知識庫裡，兩種檢索看不出差別。

### 八、實驗二：v4

v4 從 v3.2 改兩處：刪掉「不說出任何數字」，加一段 `<knowledge>`，分三段管三件事。第一段是知識庫沒寫的事直接說「這個我這邊沒有確切資料」；第二段是問價格時說出區間，但不能替任何一隻貓報價；第三段是客人問到接貓、準備、價格、付款或說出想要的品種時，回答完一定要邀請他留聯絡方式。

```
<knowledge>
（v4 新增）回答品種特性、健康照護、看貓接貓流程、付款、合約相關的問題時，以知識庫查到的內容為準，不要用自己的印象補充數字、病名或流程。知識庫沒有寫到、或寫著「請貓舍填寫」的事，直接說「這個我這邊沒有確切資料」，再請對方留下聯絡方式，由貓舍回覆。

對方問價格時，說出知識庫裡的價格區間，讓對方先評估預算，並說明實際價格依每隻貓的血統、花色、性別而不同，由貓舍真人回覆。不可以說出區間以外的數字，也不可以替任何一隻貓報價。

對方問到接貓、準備用品、價格、付款，或說出想要某個品種時，代表他已經在認真考慮。用知識庫回答完之後，最後一定要加一句邀請他留下稱呼與聯絡方式，例如：「如果想看看目前有哪些寶寶，方便留個稱呼跟聯絡方式嗎？貓舍會直接跟你聯繫。」不可以只叫對方「自己去問貓舍」。
</knowledge>
```

只重跑四題。價格那段穩定生效（K6）。沒資料那段讓 K12 逐字用上「這個我這邊沒有確切資料」，再請對方留聯絡方式。K4 是回歸測試，七樣照樣全到。導流那段最不穩：K6、K12 有，K10 只有一句被動的「如果需要，我可以幫你留」，K4 完全沒有，回完七樣就結束了。

導流失敗的模式很一致：問題本來就該交給真人時（價格、保固），導流自然出現；需要說明一串內容時（接貓清單），講完就收尾。模型把導流當成「答不出來時的退路」，而不是「每次都要做的事」。v4 那段每輪固定多花約 240 tokens。

### 九、根據結果改寫知識庫 v2

實驗跑完之後，照三種失敗的原因改寫知識庫。每一段都寫明是哪些品種，例如「短腿（曼赤肯、長毛曼赤肯、小步舞曲）的健康照護」，對應 K2、K5；每個主題獨立一段、加上 `##` 標題，分期獨立成「可以分期嗎」，對應 K13；在腎臟那段寫明「腎臟屬於泌尿系統」，段落標題也盡量寫成客人會問的句子，對應 K15。另外把貓舍公開的訂貓流程、定金與退還規則、付款方式、交貓方式補進來。

v2 用 `##` 切成 19 段，每段 64 到 211 字。最大長度如果設 400，Coze 會把相鄰兩三段合併，只剩 7 段；要設成略大於最長那段（220），才會大致一段一個主題。

### 十、觀測：每一題花了多少

34 次的數字都整理在[測試集試算表](https://docs.google.com/spreadsheets/d/163Zljl8kuY-M_BAvrW1HLPSp5-9Dcs4yvjzrYTafbkk/edit)的「W4觀測」分頁，平均值和增加比例都是用公式算的。沒有知識庫時，13 題的 prompt_tokens 都在 2,628 到 2,650 之間，平均每題 total 約 2,720。掛上知識庫後平均約 3,474，多了 28%，但每題差很多：一段都沒找回的（K7、K13）一點都沒多，找回一段的多約 570，找回四段的（K9）多了約 1,380。成本不是固定的，而是看這一題找回幾段。cached_tokens 34 次全部是 0。

## 業界怎麼解

挑錯段（K5）。業界會先多找幾段，再用另一個專門排序的模型重新打分，把真正相關的排到前面，這叫 reranking。另一個做法是在檢索之前，先讓模型把客人的口語問題改寫成適合檢索的句子，例如把「小步舞曲腿短會不會比較容易生病」改成「短腿貓健康照護注意事項」，這叫 query rewriting。

一段都沒挑中（K13）。根本解法在資料：一段只講一件事，而且每段自己看得懂，不依賴其他段落的定義。業界也常把知識庫寫成問答形式，或替每一段預先產生「客人可能怎麼問」，讓問句和段落更容易對上。

挑對了卻沒用上（K15）。業界會要求模型回答時標出引用了哪一段，讓「有資料卻沒用」被看見；或者先讓模型判斷每段資料跟問題的關係，再作答。

不相關的段落也被塞進來。K1 的第三段是價格區間，分數只有 0.56，跟遺傳疾病無關，還是被塞進去花錢。業界會把分數門檻設嚴一點，或用 reranking 只留最相關的一兩段。

知識庫蓋過 prompt。這次是好結果，但反過來就是間接 prompt injection 的風險：如果有人在被檢索的文件裡夾帶指令，或知識庫放了錯的資料，守門的 prompt 擋不住。業界會把知識庫當成「不可信的輸入」，在 prompt 裡寫明檢索內容只能當資料、不能當指令，並且讓 prompt 和知識庫的規則一致，不靠互相覆蓋。

會一直變的資料。在籍名單和個別價格，業界通常不放知識庫，而是放在資料庫，由 agent 透過工具即時查詢。這接回單元 3 的資料表，也接到之後自己做 API 的方向。

導流不穩定。不靠模型記得，而是在流程裡偵測購買意願，由固定的節點在回答後面接上留資料的邀請，或直接跳出表單。這是單元 6 的工作。

## 踩坑與排除過程

把檔案拖進聊天框當成知識庫。模型回答「無法處理這個連結」。聊天框的附件只會傳給那一輪對話，而且模型沒有讀檔工具；知識庫要在 agent 編輯頁的 Knowledge 區塊建立再掛上去。

預覽畫面跟實際分段不一樣。預覽看到四段，除錯面板找回來的段落卻有預覽裡沒出現的切法。判斷分段結果，要以實際被找回來的 slices 為準。

測試題設計錯誤。K9 原本想測「問句沒有關鍵字，語意檢索也找得到」，可是知識庫那句寫著「多囊腎是腎臟長出囊泡」，問句裡的「腎臟」字面就對得上，測不出差別，後來改用 K15 的「泌尿」。K8 原本想測 top-k，但自訂分段後兩半答案一度看起來在同一段，所以加了跨段的 K14；後來從 slices 發現 K8 其實也是跨段。設計測試題時，要先確認題目真的只測想測的那一件事。

分段的最大長度設太大。v2 用 `##` 切成 19 段，最大長度 400 卻只得到 7 段，因為 Coze 會把相鄰的小段合併到接近上限。最大長度要略大於最長的一段。

## 對應到我的專案

第一件事，知識庫要用寫給「只看得到片段的人」的方式寫。我原本的寫法是給人從頭讀到尾的，「長腿」「短腿」定義一次就一直用。可是 agent 每次只看到兩三段，每一段都要自己說得清楚。這也是貓舍其他文字（IG 圖卡、私訊範本）可以改進的地方：客人通常也只看到其中一張。

第二件事，知識庫和規則要一起管理。價格這題讓我發現，同一件事寫在 prompt 和知識庫兩個地方，遲早會打架。之後改價格區間、改定金規則，要知道兩邊都要改，或者只放在一邊。

第三件事，答案變準不等於生意變好。知識庫讓 agent 答得更準，卻讓它忘了請客人留聯絡方式。對貓舍來說，一個把接貓清單講得完整、但沒留下名單的對話，價值比一個答得普通、但拿到聯絡方式的對話低。期末的選種顧問，導流一定要用流程保證。

第四件事，成本會跟著知識庫變大。現在知識庫只有幾段，平均多 28%；之後品種介紹、照護文章越加越多，每題找回的段落、花的 token 都會增加。分數門檻和 top-k 不只是準確度的設定，也是成本的設定。
